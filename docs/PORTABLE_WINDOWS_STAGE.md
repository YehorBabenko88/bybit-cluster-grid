# Offline Windows component staging

This preparation does not install the six-module release. Python wheels and Consul remain unresolved in the Root catalog; installation closure remains false and the overall decision remains `NO_GO`. There is no publisher authentication, physical grant, Windows service installation, firewall change, global PATH change, or high availability qualification.

`installer/Stage-PortableWindowsRuntime.ps1` accepts external hashes for its adjacent `PortableRuntime.psm1`, the exact Root catalog, the raw Root package preflight, the Root source guard, and `NativeJobProcess.cs`, plus exact Root Git HEAD/tree. The caller must obtain those pins from its reviewed source/release configuration, rather than calculate trust pins from an untrusted input directory. The entrypoint itself must be selected from the caller's pinned Grid source. No network acquisition occurs in either mode.

`Prepare` is the default. It requires all five catalog archives in `ArtifactRoot`, verifies their compressed byte hashes and sizes, and reads bounded ZIP metadata. It does not create `StageRoot`, run Python, or execute an SDK. Missing or malformed archives produce a blocking result. `PREPARED_INPUTS_ONLY` describes these inputs and never grants execution or installation authority. The full Root source fence is executed only in explicit ephemeral mode, after its Python/Git bootstrap exists; Prepare does not claim that source fence passed.

`EphemeralCI -AuthorizeEphemeralWindowsCI` additionally requires a GitHub-hosted Windows environment, a fresh child of `RUNNER_TEMP`, fixed local non-reparse ancestors, a machine name outside the explicitly excluded office names, and adequate free space. Environment checks constrain intended operation; they are not a cryptographic identity or owner grant. The current implementation assumes this fresh namespace has one trusted writer. It is not a sandbox against another process with the same filesystem authority.

Extraction validates the central directory before .NET materializes entries: compressed and expanded budgets, file count, single-disk non-ZIP64 metadata, supported compression, ASCII Windows namespace, ZIP slip, ADS, reserved devices, ambiguous names, case-insensitive duplicates, file/directory collisions, and link/reparse metadata. Output uses fresh files and records hashes of extracted bytes. Executable hashes are derived from these verified archive streams; an archive hash is never treated as an executable hash.

Only Python and MinGit are extracted first. Pinned Python runs `-I -S -B` and the externally pinned Root `package_preflight.py --operation toolchain`, with exact Root source IDs/guard hash and the extracted Git executable/hash. The Root helper must report all five `BYTES_MATCH`, component-only verification, unresolved global dependencies, no installation closure, no services and no authority. A fresh cache is removed by that helper. Child processes receive a small private environment, bounded output and deadlines; inherited Python configuration, PATH, Git configuration, and PostgreSQL connection settings are not forwarded.

The native C#5 helper is compiled lazily only after the explicit ephemeral gate. It uses restricted inherited handles, `CreateProcessW(CREATE_SUSPENDED)`, a kill-on-close Windows Job, assignment before `ResumeThread`, bounded pipe drains and an absolute deadline. Setup/assignment failure terminates the still-suspended root. Closing the Job also kills descendants when their parent has already exited. Ordinary helper jobs close after the invocation; the PostgreSQL start job remains owned until explicit stop or stage-finally cleanup. This helper is reusable process containment, not an SCM host or a ProcessDriver integration claim.

After that boundary, actual vendor components must pass pinned-version checks. Python creates a private venv without pip or global site packages; no `.pth` file is permitted. PostgreSQL initializes a fresh data directory, binds a randomly selected loopback port, verifies that connection's data path/port/version, and stops that owned cluster. No existing database, cluster, service or data directory is used. NSSM runs only its version command; no SCM operation occurs. A failure attempts an owned `pg_ctl -D <private-data> stop`, records cleanup failure, and preserves the stage for review. It does not recursively delete a possibly active database.

## Native verification entrypoints

Run both scripts under Windows PowerShell 5.1 and PowerShell 7 on actual GitHub-hosted Windows runners:

- `installer/native-job.security.tests.ps1 -NativeJobSha256 <external-pin>`: actual harmless parent/child heartbeat, retained-job lifetime, and real Job-assignment failure before resume. The fixture uses the local Windows .NET Framework compiler; it never substitutes for vendor SDK qualification.
- `installer/portable-runtime.security.tests.ps1`: harmless synthetic ZIP path/resource/extraction tests. These never qualify vendor SDKs.
- `installer/portable-runtime.smoke.tests.ps1 -RequestFile <local-json>`: real five-archive Prepare followed by actual component smoke. Missing archives are errors, never skips.

The request JSON has exactly these string keys: `ArtifactRoot`, `StageRoot`, `UnifiedRoot`, `UnifiedSourceHead`, `UnifiedSourceTree`, `CatalogSha256`, `PreflightSha256`, `SourceGuardSha256`, `LibrarySha256`, `NativeJobSha256`. The caller pins source and helper bytes before invoking this wrapper. Each matrix cell needs its own fresh StageRoot and real pinned archive set. The wrapper checks that Prepare leaves StageRoot absent and the final result retains `NO_GO`, no installed services, false installation closure and stopped private PostgreSQL.

At authoring time the first three archives were hash-verified and inspected without executing them on Linux; their expected Python, Node and Git paths were present. PostgreSQL/NSSM archive availability, native PowerShell parsing, ZIP tests, all SDK execution, isolated PostgreSQL start/stop, and both native engine cells are **NOT_RUN**. No complete offline runtime, six-module install, activation, live/paper system, office rollout or physical readiness is claimed.
